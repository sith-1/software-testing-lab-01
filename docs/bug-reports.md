## 0. Соглашения

**Окружение.** Все три дефекта наблюдались в тестовой версии системы. В отчётах указано окружение, необходимое для воспроизведения; точные идентификаторы сборки и тестового стенда подставляются при публикации дефекта в трекере — они не входят в репозиторий лабораторной по требованию «без служебных данных и персональных данных».

**Ожидаемый результат.** Ожидания сформулированы на основе исходных требований. Там, где требование допускает толкование, в отчёте прямо указано, какой критерий используется и какой вопрос из `docs/requirements-review.md` его определяет. Ожидание, придуманное без основания, в отчёт не включается.

**Шкалы.**

| Серьёзность | Значение |
| --- | --- |
| Критическая | Утечка или потеря данных, обход ключевого ограничения, юридическое нарушение |
| Высокая | Основной сценарий недоступен для части пользователей либо нарушается целостность данных |
| Средняя | Некорректное поведение с обходным путём, неудобство, искажение сообщения |
| Низкая | Косметический дефект, не влияющий на результат |

| Приоритет | Значение |
| --- | --- |
| Критический | Исправление до выпуска, блокирует релиз |
| Высокий | Исправление в текущей итерации |
| Средний | Исправление в ближайших итерациях |
| Низкий | Исправление по возможности |

**Заголовок** описывает действие, условие и проблему. Формулировки «Ошибка регистрации» и «Не работает» не используются.

## BUG-01. Пользователь, которому исполнилось ровно 18 лет, получает отказ «Регистрация доступна только с 18 лет»

- **Окружение:** тестовый стенд регистрации (test), браузер Chrome (актуальная стабильная версия), Windows 11, разрешение 1920 × 1080, язык интерфейса русский
- **Предусловия:** открыта страница регистрации; тестовый адрес электронной почты не зарегистрирован; доступ к тестовым данным есть
- **Серьёзность:** Высокая
- **Приоритет:** Высокий
- **Связанные проверки:** CH-D-01, CH-D-03, CH-D-06
- **Воспроизводимость:** 3 из 3 попыток

### Шаги воспроизведения

1. Открыть страницу регистрации.
2. В поле «Имя» ввести «Иван».
3. В поле «Адрес электронной почты» ввести новый свободный адрес, например `ivan.test.01@example.com`.
4. В поле «Пароль» ввести пароль, удовлетворяющий политике, например `Str0ng!pass`.
5. В поле «Возраст» указать дату рождения, при которой на текущую дату пользователю исполняется ровно 18 лет (например, при дате проверки 06.11.2026 — 06.11.2008).
6. Нажать кнопку «Зарегистрироваться».

### Фактический результат

Регистрация не выполняется. Отображается сообщение «Регистрация доступна только с 18 лет». Учётная запись не создаётся. При уменьшении даты рождения на один год (17 лет) сообщение остаётся тем же, поэтому по тексту невозможно понять, что именно не так.

### Ожидаемый результат

Пользователь, которому на дату проверки исполнилось 18 лет, считается совершеннолетним и регистрируется успешно (критерий из `docs/requirements-review.md`, вопрос Q-7). Отказ и сообщение о возрастном ограничении допускаются только для пользователей младше 18 лет.

### Дополнительные материалы

- Скриншот формы с сообщением об отказе — `evidence/` (файл прикладывается при публикации).
- Значение даты рождения и системная дата сервера на момент проверки.
- Идентификатор запроса из журнала, если он отображается пользователю.
- **Гипотеза о причине (не подтверждена):** возраст вычисляется как разность годов без учёта месяца и дня, либо граница сравнивается строгим неравенством «больше 18» вместо «не меньше 18». Требует подтверждения разработчиком.

## BUG-02. Двойное нажатие кнопки «Зарегистрироваться» создаёт две учётные записи с одинаковым адресом

- **Окружение:** тестовый стенд регистрации (test), браузер Chrome (актуальная стабильная версия), Windows 11, разрешение 1920 × 1080; для проверки результата — доступ к списку пользователей тестового стенда
- **Предусловия:** открыта страница регистрации; адрес `dup.test.02@example.com` не зарегистрирован; сеть работает без задержек
- **Серьёзность:** Высокая
- **Приоритет:** Высокий
- **Связанные проверки:** CH-G-01, CH-G-02, CH-G-05, CH-E-02
- **Воспроизводимость:** 5 из 5 попыток при быстром двойном нажатии; при медленном одиночном нажатии не воспроизводится

### Шаги воспроизведения

1. Открыть страницу регистрации.
2. Заполнить все поля корректными данными: имя «Мария», адрес `dup.test.02@example.com`, пароль `Str0ng!pass`, дата рождения, дающая 20 лет.
3. Быстро нажать кнопку «Зарегистрироваться» два раза подряд, не дожидаясь ответа сервера.
4. Дождаться завершения обоих запросов.
5. Открыть список пользователей тестового стенда и найти записи с адресом `dup.test.02@example.com`.

### Фактический результат

Создаются две учётные записи с одинаковым адресом электронной почты. Пользователю показывается сообщение об успешной регистрации. На адрес приходят два письма. В списке пользователей видны две записи с разными идентификаторами и одинаковым адресом.

### Ожидаемый результат

Создаётся ровно одна учётная запись. Кнопка блокируется на время выполнения запроса, повторный запрос не отправляется или отклоняется сервером. При параллельной отправке двух запросов второй получает ответ 409 и сообщение о конфликте (критерии CH-G-01 и CH-G-05, вопрос Q-13). Уникальность адреса должна обеспечиваться ограничением в базе данных, а не только проверкой перед вставкой.

### Дополнительные материалы

- Журнал сетевых запросов браузера (HAR) с двумя одновременными запросами на создание учётной записи.
- Идентификаторы обеих созданных записей.
- Скриншот списка пользователей с дубликатом.
- **Гипотеза о причине (не подтверждена):** отсутствует блокировка кнопки на клиенте и отсутствует уникальный индекс по адресу в базе данных; проверка уникальности выполняется отдельным запросом до вставки.

## BUG-03. При вводе существующего адреса электронной почты сообщение об ошибке содержит полный объект пользователя

- **Окружение:** тестовый стенд регистрации (test), браузер Chrome (актуальная стабильная версия), Windows 11, разрешение 1920 × 1080; инструменты разработчика открыты для просмотра ответа сервера
- **Предусловия:** в системе существует учётная запись с адресом `existing.test.03@example.com`, у неё заполнены имя и дата рождения
- **Серьёзность:** Критическая
- **Приоритет:** Критический
- **Связанные проверки:** CH-B-06, CH-F-06, CH-E-05
- **Воспроизводимость:** 3 из 3 попыток

### Шаги воспроизведения

1. Открыть страницу регистрации.
2. Заполнить поля корректными данными, указав в поле адреса уже существующий адрес `existing.test.03@example.com`.
3. Нажать кнопку «Зарегистрироваться».
4. Прочитать сообщение об ошибке на странице.
5. Открыть панель разработчика, вкладку «Сеть» и посмотреть тело ответа сервера на запрос регистрации.

### Фактический результат

В сообщении об ошибке отображается служебный текст, содержащий полный объект пользователя: идентификатор записи, имя, адрес электронной почты, дата рождения и служебные поля базы данных. Тот же объект возвращается в теле ответа сервера. Любой пользователь, вводящий адрес, может получить персональные данные его владельца, не имея доступа к учётной записи.

### Ожидаемый результат

Пользователь видит нейтральное сообщение о том, что адрес уже используется (критерий из вопроса Q-14), без имени, идентификатора, даты рождения и служебных полей. Ответ сервера содержит только код ошибки и машинно-читаемый идентификатор сообщения, а не объект пользователя. Полные сведения о конфликте пишутся в журнал с маскированием персональных данных (вопрос Q-29).

### Дополнительные материалы

- Скриншот сообщения на странице с видимым объектом пользователя.
- Тело ответа сервера (JSON) и код ответа.
- Идентификатор владельца адреса, чтобы подтвердить, что это существующая запись.
- **Гипотеза о причине (не подтверждена):** обработчик конфликта уникальности возвращает пользователю исходное исключение базы данных или собранный объект существующей записи вместо кода ошибки.

**Приоритет исправления BUG-03 выше, чем BUG-01**, хотя оба дефекта серьёзные: утечка персональных данных необратима и не требует от пользователя никаких особых действий — достаточно ввести чужой адрес. Ограничение по возрасту, напротив, можно смягчить ручной проверкой службы поддержки, поэтому исправляется во вторую очередь.

Разница между серьёзностью и приоритетом видна на BUG-02: серьёзность высокая, потому что нарушается уникальность учётной записи и образуются дубликаты, но приоритет высокий, а не критический, — дефект не приводит к потере или утечке данных, а уже созданные дубликаты можно слить скриптом.
