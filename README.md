## Вывод

**1. Можно ли начинать реализацию без уточнений?** Нет. Ни одно требование не проверяемо: не определены термины («имя», «надёжный», «корректный»), не заданы границы, не описано поведение. Разработчик сам выберет значения, и тестировать придётся его догадку, а не требование. Сначала — ответы на Q-1…Q-33.

**2. Три риска для первоочередного тестирования.** R-02 (утечка пароля и персональных данных — необратима), R-01 (повреждение данных регистрации — не восстанавливается из интерфейса), R-03 (регистрация несовершеннолетнего — юридическое нарушение, кодом не исправляется).

**3. Что автоматизировать первым.** Логику полей и границы (CH-A-02, CH-A-03, CH-B-05, CH-C-03), границу 18 лет (CH-D-03), защиту от дубликатов (CH-G-01, CH-G-05 — вручную два запроса синхронно не отправить), проверку отсутствия утечек в ответах (CH-F-06).

**4. Что требует человека.** Понятность сообщений (CH-B-09, CH-F-02), доступность (CH-E-04, CH-F-01), отказоустойчивость (CH-F-04), приёмочная оценка продукта.

**5. Что нужно для решения о готовности.** Согласованные критерии приёмки; результаты прогона чек-листа с причиной каждого непройденного пункта; отсутствие дефектов критической и высокой серьёзности; результаты нефункциональных проверок (время ответа, отказ БД, отсутствие данных в журналах); юридическая готовность (согласие на обработку персональных данных, срок хранения, удаление).
